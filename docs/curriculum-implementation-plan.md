## 0.1 検討事項(未決定、議論を後で再開する)

### 類題(反復練習)の提示方法 — 2026-10-15 ユーザー提起

完了基準の条件2(「基本型に加え、数値・条件を変えた問題を用意する」)を満たすため、各タイプに類題を複数用意していく方針だが、**学習者にどう見せるかは未決定**。今実装はしないが、論点として記録しておく。

- 1問見たらすぐ次のタイプに進みたい学習者もいれば、同じタイプの類題を連続して反復練習したい学習者もいる。両方のニーズがありえる。
- 固定運用(常に類題を連続提示する／常に1問ずつ別タイプに進む)にするか、学習者が選べるようにするか未定。
- 現状の演習問題一覧は「1タイプ1問」が並ぶ形式。類題を増やしたときに、同じ一覧に別問題として並べる(現状の自然な延長)か、「同じタイプの類題に挑戦する」という別の導線(例: 正解後に「もう一問」ボタン、間違えたときだけ類題を出す、等)を作るかで設計が変わる。
- トピック学習画面(セクション1の方針)を作る単元では、トピック内で扱う問題タイプそれぞれに類題が複数ある状態になりうるため、トピック学習と演習問題の両方でこの論点に関わる。

次に議論する際の切り口:
1. 類題は「演習問題一覧に別カードとして並べる」か「1つの問題を解いた後に類題へ続けられる導線を作る」か
2. 反復したい／したくないを学習者が選べるUIにするか、それとも一律の運用にするか
3. 間違えたときだけ類題を出す(弱点補強)という使い方も含めて検討するか
4. 上記はトピック学習画面の設計(セクション1・将来のCodex実装依頼)にも影響するため、トピック画面の実装に入る前に一度結論を出すか、仮運用で進めながら調整するか

## 0.2 解説スタイル・インタラクション標準の確立(2026-10-15〜17、確定)

計算・数の処理(u6-calc)を題材に、ユーザーレビュー→VISTA外のArtifactデモ(「くふうラボ」)での検証を経て、以下を標準として確定・実装済み。

### 解説の構成・口調
- `solution`の構成: 【ポイント(問題ごとの具体名)】→【解説】(①②③でポイントに言及しながら説明)→【広げてみよう】→【別解】(任意)→【確認】→答え。詳細は`docs/content-authoring.md`。
- 口調は「ちょうどいい」(語りかけるが煽らない、感嘆符や幼児向けの相槌は使わない)を標準とする。基準文例も`docs/content-authoring.md`に記載。

### トピック画面のインタラクション標準(2つ)
VISTA外のArtifact(くふうラボ)でユーザーが実際に触って検証した上で採用。u6-calc-screenの「基本例題」に実装済み(`specs/2026-10-16-calc-topic-interaction-upgrade.md`)。

1. **発見ミニパズル+その場限りのご褒美**: 複数の選択肢(数字・図形の組み合わせ等)から2つを選ぶと、その場で結果がプレビューされる。「きれいな答え」に気づいたら軽い演出(キャラの反応+ひとこと+きらめき)。正解以外を選んでも怒らず「他も試してみよう」と優しく再挑戦を促す、ペナルティなし。演出は学習記録に残さない(恒久的なバッジ・コレクション機能は不採用)。
2. **「大変さ」のビフォーアフター**: 速さ・時間を一切測定・表示しない。「ふつうに解くと(大変)」→「くふうすると(らくらく)」の順で、同じ結果に至る2つの道筋の負担の違いを見せる。採用されなかった案: 2レーンの競走形式(計算する人によって時間が変わり基準があいまいという理由で不採用)。

いずれも、他単元のトピック画面でも再利用できる一般パターンとして想定しているが、仕掛けの中身(何をタップ・何を重ねるか)は問題タイプごとに個別設計が必要(0.3節参照)。

## 0.3 平面図形への応用検討(2026-10-17、未決定・議論中)

ユーザーから「平面図形を優先して完成させ、早くフィードバックを得たい」との意向が示された。0.2節の2つのインタラクション標準を平面図形に翻訳できるか、VISTA外のArtifact(「図形ラボ」)で2つの未実装タイプを題材に試作し、ユーザーと議論を開始した(結論は未確定)。

### 翻訳の方針(試作時点の仮説)
- 計算の「数字のペア探し」→ 図形では「補助線を引く」「図形を重ねる」という発見に置き換える。
- 計算の「大変さ」の表現(ゆっくり/すばやく、速度の違い)→ 図形では「手がかりなし(詰む)→2stepで解ける」という状態の違いで表現する方が自然。
- 「ちょうどいい」口調はそのまま図形の解説にも適用できそうという手応え。

### 試作した2例
1. **花びら形の面積(P-17、円と正方形・重なり・斜線の面積、現状「無」)**: 1辺10cmの正方形+対角2頂点を中心とする半径10cmの四分円2つ。「公式が直接ない→詰む」状態から、「四分円を重ねてみる」操作で花びら部分が二重カウントされていることを色の重なりで可視化→ 78.5×2－100＝57cm²。広げてみよう先: 場合の数の「重なりの除外」、集合の問題と同じ考え方。
2. **補助線で角を求める(P-01、平行線・対頂角・三角形の角、現状「無」)**: 平行な2直線の間で折れ曲がる角x(定番のZ字型)。「手がかりなし」から「補助線を引いてみる」操作で角が錯角2つに分かれる様子を見せる→ 50°+35°=85°。広げてみよう先: 同種のZ字型・N字型すべてに使える最重要パターンである旨。

### 残る論点(ユーザー提起、2026-10-17)
1. 発見の仕掛け自体(何をタップ・何を重ねるか)は問題タイプごとの個別実装が前提になりそう。「発見→ご褒美」の演出パターンだけは共通化できる見込み。
2. 大変さの表現を「状態の違い(詰む→2step)」にする方向で良いか。
3. 平面図形を優先する場合の工数見積り: 図形は毎タイプSVG+発見の仕掛けが必要で、計算・数の性質のような文章のみのスプリントより工数が大きい見込み。1スプリントあたり1〜2タイプ程度を想定した方が現実的ではないか。
4. 平面図形は既存19問に一切触れず追加のみ、という制約は維持する前提で進める。

次のアクション: ユーザーからのフィードバックを受けて、上記論点に結論を出してから最初の実装スプリント(候補: P-01またはP-17)のPlanner specを作成する。

## 5. 運用ルール(再掲)

- 新規ファイルを作る分野(数の性質・場合の数・立体図形・グラフ)は、最初の1問を追加する時点で`index.html`・`data/problems.js`への登録をまとめて行う。
- 既存ファイルに追記する分野(割合・特殊算・速さ・計算)は、該当ファイルの末尾に追記するだけでよい。
- 各スプリント完了時のチェックリスト(Sprint1を踏襲):
  1. `node scripts/validate-content.cjs` が0エラー
  2. `npm test` が全件pass(`tests/catalog.test.cjs`の問題総数アサーションを更新)
  3. Playwrightで実ブラウザ確認(該当カテゴリが開けて採点できる)
  4. coverage-final.md・plan・coverage-final.jsonの該当行・集計を同期
  5. VISTA.md(PM)・specs/に記録
- 視覚化(トピック画面)が必要かどうかは、まず演習問題(非視覚)を先に揃え、十分な問題数が揃った分野から個別にユーザー・Codexと相談して着手する(平面図形・割合・特殊算・速さと同じ発展パターン)。
